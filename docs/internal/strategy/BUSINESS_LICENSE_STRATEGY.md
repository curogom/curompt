# 사업화 고려 라이선스 전략

## 상황 분석

**목표:**
- Public 저장소로 공개 (마케팅, 포트폴리오, 커뮤니티)
- 팀 단위 사업화 가능성 (향후)
- 현재는 오픈소스로 시작하되, 상업적 가치 보호 필요

## 추천 전략: BSL (Business Source License) 1.1

### 왜 BSL인가?

**장점:**
1. ✅ **Public 저장소 가능**: 소스 코드 공개 (GitHub Public)
2. ✅ **상업적 보호**: 일정 기간 동안 상업적 사용 제한 가능
3. ✅ **전환 보장**: 지정된 시점 후 완전 오픈소스로 전환
4. ✅ **유연성**: 라이선스 조건 커스터마이징 가능
5. ✅ **투명성**: 소스는 보이지만 사용 조건 제한

**예시 조건:**
```bsl
Additional Use Grant: 
- 이 소프트웨어는 개인, 교육, 연구 목적으로 사용 가능합니다.
- 상업적 용도(팀 단위 배포, 서비스 제공 등)에는 
  CuroGom의 명시적 허가가 필요합니다.

Conversion Date: 
- 4년 후 (2029년 1월 1일) MIT License로 자동 전환
```

## 대안 전략

### 1. Dual License (이중 라이선스)
**구조:**
- Community Edition: Apache 2.0 (Public)
- Enterprise Edition: 상업용 라이선스 (유료)

**장점:**
- 명확한 라이선스 분리
- 기능 차별화 가능

**단점:**
- 코드 관리 복잡
- 두 버전 유지 필요

### 2. Source Available + Commercial License
**구조:**
- 소스는 Public (보기만 가능)
- 사용은 라이선스 필요

**예시:**
- CockroachDB, MongoDB 스타일

**장점:**
- 소스 투명성
- 상업적 보호

**단점:**
- "오픈소스"로 인정 안 될 수 있음
- 커뮤니티 기여 제한적

### 3. AGPL + Commercial (MongoDB 방식)
**구조:**
- AGPL로 공개 (강한 copyleft)
- 상업용은 별도 라이선스 판매

**장점:**
- 명확한 상업적 보호

**단점:**
- AGPL은 기업들이 피하는 경향
- Public 저장소에 부정적 이미지
